## 1. DB の耐障害性（既存 + 段階12）

| 項目 | 内容 |
|---|---|
| ジャーナル | WAL |
| 同期 | `synchronous = FULL`（コミット済みのトランザクションは電源断後も残る） |
| トランザクション | すべての記録操作は「データ + 操作履歴」を 1 つの IMMEDIATE トランザクションで保存（段階2） |
| 削除 | 全テーブルで物理削除をトリガーで拒否。履歴・時計遷移・起動記録は追記専用 |
| 時計 | 状態遷移を追記で保存し、経過時間は毎回再計算（段階4）。再起動後も同じ値に戻る |

## 2. 起動時の整合性チェック（D-065）

1. DB ファイルがなければ新規作成（初回起動）。DB がなく WAL だけ残っている場合は停止する。
2. DB 本体と `-wal` を一時フォルダへコピーし、**コピーを開いて** `PRAGMA integrity_check` と `PRAGMA foreign_key_check` を実施する。
   - コピーを開くと SQLite が WAL を適用するため、**WAL にある確定済みデータも検査される**（未確定の書き込みは含まれない）。
   - 元ファイルを読み取り専用で開く方法では、SQLite が `-shm` の作成や WAL の復旧処理を行う可能性があるため採用しない。
3. 問題がなければ書き込み可能な状態で開き、設定を適用してからマイグレーションを行う（**整合性チェックはマイグレーションより前**）。
4. 異常（開けない、DB ではない、integrity_check が ok でない、参照整合性の違反がある）があれば、書き込み可能な状態では開かず、エラー内容と対処方法を表示して起動を停止する。自動修復・自動上書きはしない。**元の DB・WAL は変更しない**（テストでハッシュ・更新日時・サイズを確認）。
- 一時フォルダには DB のコピーが一時的に置かれ、検査後に削除する（DB と同程度の空き容量が必要）。

## 3. 起動・正常終了の記録（D-066、マイグレーション 004）

テーブル `app_lifecycle_events`（追記専用、操作履歴・UNDO とは無関係）：`BOOT` / `CLEAN_SHUTDOWN` / `SUSPEND` / `RESUME`。

- 起動時：起動セッション（`app_sessions`）と `BOOT` を同じトランザクションで記録する。
- 判定：現在の起動より前で `BOOT` がある最も新しい起動に `CLEAN_SHUTDOWN` がなければ「前回は異常終了」。起動時に警告ダイアログを表示し、検証用画面にも表示する。
  `BOOT` がない起動（マイグレーション前）は判定しない（古い起動をまとめて異常終了と誤判定しないため）。

### 正常終了の手順と誤判定の扱い

```
1. 終了処理中にする（以後、通常の IPC 経由の操作はすべて拒否。起動情報と状態の問い合わせのみ例外）
2. 電源の抑制を解除
3. アプリの DB 接続を閉じる ── 閉じられなければ CLEAN_SHUTDOWN を書かない（= 次回「異常終了」）
4. 閉じられた場合のみ、別の短い接続で CLEAN_SHUTDOWN を 1 件追記して閉じる（通常の書き込み経路・IPC とは分離した内部処理）
```

- CLEAN_SHUTDOWN を「アプリの接続を閉じた後」に書くため、「CLEAN_SHUTDOWN を書いた後、アプリの接続を閉じる前に落ちた」ことによる正常終了の誤判定は起こらない。
- **DB のクローズに失敗した場合は正常終了扱いにしない。**

### 残る限界（完全には検出できないタイミング）

| タイミング | 判定 | 影響 |
|---|---|---|
| 手順 3 と 4 の間で落ちた | 異常終了（安全側の誤判定） | 記録は確定・クローズ済み。通知が出るだけ |
| 手順 4 の記録用接続で、CLEAN_SHUTDOWN の確定後・接続を閉じる前に落ちた | 正常終了 | アプリの記録はすべて確定・クローズ済みで、記録用接続が書いたのはこの 1 件だけのため、記録の欠落はない（WAL は SQLite が次回復旧する） |
| ストレージの書き込みキャッシュが電源断時に失われる等、OS・ハードウェアがコミット済みデータを保持しなかった | 検出できない | SQLite の保証の範囲外 |

## 4. 電源管理（D-063）

- 進行中（RUNNING / PAUSED）の大会が 1 つ以上あれば、Electron の `powerSaveBlocker.start('prevent-display-sleep')` で**ディスプレイの自動消灯と自動スリープを抑制**する。
- 再判定のタイミング：START・PAUSE・RESUME・END の確定直後、アプリ起動時（異常終了後の再起動でも抑制を復元）、正常終了時（解除）。
- 抑制要求はプロセスに紐づくため、**異常終了・強制終了時はプロセス終了とともに OS が解除する**（Windows 実機で `powercfg /requests` による確認が必要）。
- OS の電源プランは変更しない。
- 電源 API の失敗は、時計の記録処理に影響させない（記録は成功し、失敗はログに残す）。
- アプリでは防げないもの：ノート PC のフタを閉じる操作、電源ボタン、ユーザーによる手動スリープ、バッテリー残量低下による強制スリープ、グループポリシー等の制限。

## 5. スリープ・休止からの復帰（D-064）

- OS のスリープ通知・復帰通知（`powerMonitor` の `suspend` / `resume`）で `SUSPEND` / `RESUME` を記録する。
- 復帰時の「PC 実日時 − マスタークロック」と、スリープ時（通知がなければ最後に確認した時点）のずれを比べ、**変化が 5 秒を超えたら** `anomaly = 1` として記録し警告を表示する。
- 時計の基準は取り直さず、レース時間も補正しない。復帰後の記録は、起動セッション ID と RESUME の日時から「時刻異常の可能性あり」と識別できる（CSV の列は変更しない）。
- 背景：マスタークロックは単調増加時計で進むため、OS によってはスリープ中に止まる可能性がある（Windows 実機での確認が必要）。

## 6. ウィンドウを閉じる・OS の終了（D-067）

- 進行中の大会がある状態でウィンドウを閉じようとすると、確認ダイアログ（キャンセル / 終了する）を表示する。
- Windows のシャットダウン・ログオフ（ウィンドウの `session-end`）では確認ダイアログを出さず、正常終了の手順で閉じる。`session-end` で正常終了の手順が始まると終了処理中になり、以後の close では確認ダイアログを出さない。
- Electron 33（D-073）には事前通知の `query-session-end` がないため、OS が先にウィンドウを閉じようとした場合に確認ダイアログが出る可能性が残る（Windows 実機での確認が必要）。

## 7. Renderer の異常終了（D-068）

- Main プロセスと DB 接続は維持し、Renderer だけを再読み込みする。再読み込み後の画面は DB から現在の状態を再取得する。
- 二重登録の防止：記録操作は Main 側で 1 回だけ実行され、Renderer は失敗した操作を自動で再送しない。同一チーム・同一日時の重複も拒否される。
- 回数制限：**60 秒以内（ちょうど 60 秒前を含む）に最大 3 回**。超えたら自動再読み込みを停止し、エラーを表示する。

## 8. 異常終了後の復旧確認待ち（D-070〜D-072、マイグレーション 005）

| | 正常終了後の再起動 | 異常終了後の再起動 |
|---|---|---|
| 大会の状態 | そのまま（RUNNING / PAUSED） | そのまま（RUNNING / PAUSED） |
| 時計 | 停止していた時間も含めて進む | 停止していた時間も含めて進む（実際のレースは進行しているため） |
| 時計の操作記録 | 変更しない | **変更しない**（START / PAUSE 等を自動追加しない） |
| 復旧確認待ち | 作らない | 進行中（RUNNING / PAUSED）だった大会ごとに作る |
| 操作 | 通常どおり | 確認まで、その大会のメモ以外の書き込みを拒否（D-071） |
| スリープ抑止 | 進行中の大会があれば維持 | 確認待ちの間も維持 |

- 記録：追記専用テーブル `race_recovery_holds`。`HOLD`（システムが作成、異常終了した起動の ID と検出時の大会状態付き）と `CONFIRM`（操作者名のスナップショット付き、`hold_id` で HOLD を参照、1 つの HOLD に 1 件まで）。確認待ち = CONFIRM のない HOLD。
- 操作履歴にも、確認待ちの作成（操作者なし、`recovery hold (system, unclean shutdown)`）と確認（`recovery confirmed`）を追記する。UNDO の対象外。既存の時計操作記録・ラップ記録・操作履歴は変更しない。
- DB に保存するため、再起動・Renderer の再読み込みで確認待ちは消えない。確認前に再び異常終了しても重複して作らない。確認前に正常終了した場合も確認待ちは残る。
- **確認は時計の再開操作ではない**：確認しても大会の状態・経過時間は変わらない（PAUSED は PAUSED のまま）。
- 拒否はサービス層で行う（IPC 以外の経路からも迂回できない）。拒否する操作：ラップ・通過（登録・追加・修正・削除）、時計操作、開始時刻の修正、強制停止時間、UNDO、車両データ、チーム・大会情報の編集。受け付ける操作：閲覧（順位・戦略・警告・CSV を含む）、メモ、操作者の切り替え、復旧確認。
- 前回の終了が判定できない場合（このテーブルができる前の起動の後）は確認待ちを作らない。
