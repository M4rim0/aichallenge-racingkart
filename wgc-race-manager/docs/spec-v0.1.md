## 1. プロジェクト概要

### 1.1 目的

WGCなどのソーラーカーレースにおいて、ホームストレートを通過する各チームの情報を記録し、レース状況の把握および戦略判断を支援するアプリケーションを開発する。

単なるストップウォッチではなく、以下の3機能を中心とする。

1. レース管理・通過記録
2. 自チームの車両データ記録
3. 全チームを対象とした戦略分析・順位予測

AI機能は必須としない。AIを使用しなくても戦略支援システムとして十分に機能することを優先する。

### 1.2 基本要件

* Windows上で動作すること
* インターネット接続なしで全機能を利用できること
* 入力と表示は同一PCで行うこと
* 手動入力を基本とすること
* 記録はSQLiteに保存すること
* アプリの再起動・異常終了後にデータを復旧できること
* 大会ごとにデータを独立管理すること
* 過去大会の閲覧・編集・CSV出力に対応すること

## 2. 技術構成

以下を基本候補とする。

* Electron
* React
* TypeScript
* Zustand
* SQLite
* better-sqlite3
* IPC
* Repository Pattern

ただし、採用するライブラリのバージョンは開発開始時に確認し、互換性のある安定版を選択すること。

### 2.1 アーキテクチャ

責務を以下のように分離する。

* Renderer：画面表示・ユーザー入力
* Main Process：アプリケーション制御・データ処理
* Preload：RendererとMain Processの安全な橋渡し
* Repository：データベースアクセス
* Service：レース処理・戦略計算・CSV出力
* Database：SQLiteによる永続化

RendererからSQLiteへ直接アクセスしてはならない。

IPC経由で必要な操作だけを公開する。

## 3. 大会管理

### 3.1 大会情報

大会ごとに以下を保存する。

* 大会ID
* 大会名
* 開催日
* コース名
* 1周の距離
* レース開始予定時刻
* レース終了予定時刻
* 実際の開始時刻
* 実際の終了時刻
* 大会状態
* 作成日時
* 更新日時

大会状態は以下の4種類とする。

* PREPARING
* RUNNING
* PAUSED
* FINISHED

### 3.2 チーム管理

大会ごとにチームを登録する。

保存項目：

* チームID
* 大会ID
* チーム名
* ゼッケン番号
* 識別色
* 自チーム判定
* 作成日時
* 更新日時

制約：

* 1大会につき自チームは1チームのみ
* チームの追加・編集・削除に対応
* 過去大会のチーム情報を新大会へ自動流用しない
* チームを削除する際は関連記録への影響を確認する
* 記録が存在するチームを安易に物理削除しない

## 4. 時計・レース時間管理

### 4.1 マスタークロック

マスタークロックは常時動作する。

用途：

* 現在日時の表示
* 全記録の日時取得
* CSV出力時の日時情報

### 4.2 レース経過時間

レース開始操作によって計測を開始する。

レース一時停止中は経過時間を停止し、再開操作で再び進行する。

レース終了操作で停止する。

### 4.3 残り時間

予定終了時刻と現在日時を基準に算出する。

強制停止時間はレース時計を停止させず、戦略計算上の走行可能時間から除外する。

### 4.4 時計の精度

通常動作中は単調増加時計を使用し、OSの時刻変更による計測誤差を防止する。

記録には実日時も保存する。

再起動後は保存済みの日時情報を基準に状態を復元する。

### 4.5 強制停止時間

複数の停止期間を登録できるようにする。

各期間は以下を保持する。

* 停止開始日時
* 停止終了日時

停止期間が変更された場合は戦略予測を再計算する。

## 5. 自チームのラップ記録

### 5.1 基本操作

* START：計測開始
* LAP REGISTER：ラップ登録
* PAUSE：一時停止
* RESUME：計測再開
* END：レース終了

LAP REGISTERを押すと、その時点の日時を記録し、次のラップ計測へ移行する。

### 5.2 ラップデータ

* 記録ID
* 大会ID
* チームID
* 周回番号
* 通過日時
* ラップタイム
* 作成日時
* 更新日時

ラップタイムは前回通過日時との差から算出する。

最初のラップはレース開始日時を基準とする。

### 5.3 記録の修正

以下に対応する。

* 過去記録の追加
* 通過日時の修正
* 記録の削除
* 直前操作の取り消し

修正・削除後は周回番号と関連ラップタイムを再計算する。

## 6. 車両データ

ラップ記録とは独立した操作で入力できるようにする。

各ラップに以下の4項目を紐づける。

* 速度：km/h
* 電圧：V
* 電流：A
* 積算値：単位・意味は未確定

要件：

* ラップ登録後に独立して入力可能
* 1ラップにつき1セット
* 後から修正可能
* 一覧形式で確認可能
* 入力値をそのまま保存する
* SOC自動計算を実装しない
* 航続距離予測を実装しない
* エネルギー消費予測を実装しない
* 不明な積算値の単位や意味を推測しない

## 7. 他チーム通過記録

### 7.1 基本動作

参加チームすべてを記録対象とする。

各チームの通過操作によって、マスタークロックの日時を自動保存する。

自チームのラップ計測とは独立して動作すること。

### 7.2 通過記録データ

* 記録ID
* 大会ID
* チームID
* 通過日時
* 作成日時
* 更新日時

### 7.3 修正機能

* 過去通過記録の追加
* 通過日時の修正
* 記録削除
* 直前操作の取り消し

修正・削除後は対象チームのラップタイム・周回数・順位・戦略予測を再計算する。

## 8. 戦略支援システム

### 8.1 基本方針

全チームを分析対象とする。

AIに依存せず、通常の計算処理だけで予測を行う。

### 8.2 ペース分析

各チームについて以下を算出する。

* 直近3周平均
* 直近5周平均
* 直近10周平均
* ペースの変化
* 前方・後方チームとのペース差

データが不足している場合は予測を表示せず、データ不足とする。

### 8.3 順位・周回差

基本的な順位判定：

1. 周回数が多いチームを上位とする
2. 同周回の場合は該当周回の通過時刻を比較する

ただし、正式な大会規則を優先できる構造にする。

周回差と時間差は別々に管理する。

周回数が異なるチーム間の最終通過時刻の単純な差を、正確な時間差として扱ってはならない。

時間差を推定する場合は推定値であることを明示する。

### 8.4 走行位置の推定

通過記録から現在の走行位置を推定する。

基本式：

```
Q = L + Δt / P
```

* Q：推定走行位置
* L：最後に通過した周回数
* Δt：最後の通過から現在までの時間
* P：予測ラップタイム

進捗率は0〜1の範囲に制限する。

GPSやセクター計測を使用しないため、推定値であることを明示する。

### 8.5 最終周回数予測

残り走行可能時間：

```
R_drive = R_clock - S_remaining
```

* R_clock：残りレース時間
* S_remaining：今後の強制停止時間
* R_drive：残り走行可能時間

残り周回数は各チームの予測ペースから算出する。

3周・5周・10周平均をそれぞれ使用し、3種類の予測を表示する。

予測最終周回数は実際の通過タイミングを考慮して算出すること。

単純な小数部分の切り捨てだけで最終結果を決めない。

### 8.6 攻撃戦略

前方チームに追いつくために必要なペースを算出する。

相手の予測ペースをPt、必要な周回差をG、残り走行可能時間をRとした場合：

```
P_req = 1 / (1 / Pt + G / R)
```

成立しない条件では無理に数値を表示しない。

### 8.7 防衛戦略

後方チームに追いつかれないための必要ペースを算出する。

相手の予測ペースをPb、先行量をG、残り走行可能時間をRとした場合：

```
P_req = 1 / (1 / Pb - G / R)
```

分母が0以下となる場合など、計算が成立しない条件を適切に処理する。

### 8.8 最終順位予測

各チームの最終周回数を予測し、3パターンの順位を算出する。

表示対象：

* 現在順位
* 予測最終順位
* 順位変動
* 予測最終周回数
* 自チームとの周回差
* 抜ける可能性のあるチーム
* 抜かれる可能性のあるチーム
* 予測の計算根拠

実際の順位と予測順位を明確に区別する。

### 8.9 更新タイミング

以下のタイミングで再計算する。

* 新しいラップ登録
* 新しい通過記録
* 記録の追加・修正・削除
* 強制停止時間の変更
* レース終了予定時刻など予測条件の変更

### 8.10 警告

検出対象：

* 後方チームの急接近
* 前方チームを追い抜ける可能性
* 自チームのペース悪化
* 順位予測の大幅変化
* 他チームの急激なペース変化

重要度を設定する。

警告履歴は保存しない。

通知の詳細な方式・しきい値は別途確定する。

## 9. メモ機能

自由記述のみとする。

* ピットイン・ピットアウト
* トラブル
* ドライバー交代
* 天候変化
* その他

日時は自動取得する。

定型イベントボタンや独立したピット管理機能は実装しない。

## 10. 操作者管理

操作者は名前のみで管理する。

* 複数の操作者を登録可能
* レース中に切り替え可能
* 切り替え時に計測を停止しない
* 過去の履歴には操作当時の名前を保存する

## 11. 操作履歴

記録対象：

* 追加
* 編集
* 削除
* 取り消し

保存項目：

* 操作者ID
* 操作者名のスナップショット
* 操作日時
* 操作内容
* 対象データ
* 変更前の値
* 変更後の値

履歴はCSV出力する。

独立した履歴画面は実装しない。

## 12. レース終了

END操作でレースを終了する。

終了時：

* 実際の終了日時を保存
* 時計を停止
* 最終周回数を集計
* 最終順位を集計
* 各チームの平均ラップタイムを集計
* 順位変動を集計
* 予測と実績を比較
* CSV出力を可能にする

終了後も記録の追加・修正・削除に対応する。

終了した大会を再開する機能は実装しない。

## 13. CSV出力

大会ごとに以下を出力する。

* lap_records.csv
* vehicle_data.csv
* competitor_records.csv
* memos.csv
* operation_history.csv

共通仕様：

* UTF-8 BOM付き
* カンマ区切り
* CRLF改行
* ヘッダーあり
* 日本時間
* 日時はミリ秒まで保持
* 空欄は未入力として扱う
* Excelで読み込める形式とする

削除済みデータは通常の記録CSVには出力しない。

操作履歴には削除内容を残す。

同じ大会で再出力した場合は最新データで上書きする。

## 14. データベース

SQLiteを使用する。

基本テーブル：

* events
* teams
* lap_records
* vehicle_data
* competitor_passes
* operators
* memos
* operation_history
* race_clock_transitions
* mandatory_stoppages

順位・時間差・予測結果などは原則として元データから再計算する。

追加・修正・削除と操作履歴の保存は同一トランザクションで実行する。

削除操作は論理削除を基本とする。

## 15. データ保護・復旧

* SQLiteへの自動保存
* 異常終了後の復旧
* PC電源断後の復旧
* 進行中大会の状態復元
* 時計の復元
* 一時停止状態の維持

大会は一覧から選択して再開する。

定期バックアップ機能は実装しない。

USBなどへの自動バックアップも実装しない。

## 16. 電源管理

レース中はWindowsのスリープ・休止状態への移行を抑止する。

画面消灯などの電源設定についてもレース中の動作を考慮する。

レース終了後は通常の電源設定へ戻す。

アプリのバックグラウンド動作を維持する。

## 17. 実装上の禁止事項

以下を勝手に実装・変更してはならない。

* ユーザーが決めていないUIレイアウト
* ユーザーが決めていない配色
* 不要なSOC自動計算
* 不要なエネルギー予測
* 警告履歴の保存
* 定期バックアップ
* USBバックアップ
* 定型イベントボタン
* 不要なオンライン通信
* AIを前提とする戦略計算
* 記録の自動統合・自動削除

UIの具体的な構成・操作性・デザインはユーザーが決定する。

実装時にUI上の判断が必要になった場合は、勝手に決めずに保留すること。

## 18. テスト要件

以下を自動テストまたは手動テストで確認する。

### 時計

* STARTで計測が開始される
* PAUSEで停止する
* RESUMEで再開する
* ENDで終了する
* 再起動後に時計が正しく復元される
* PCの時刻変更による計測異常が発生しない

### ラップ記録

* ラップ登録で正しい通過日時が保存される
* ラップタイムが正しく算出される
* 過去記録の修正後に関連タイムが再計算される
* 削除後に周回番号が正しく再構成される

### 他チーム記録

* チームごとに独立して記録できる
* 複数チームの通過記録が混在しない
* 修正・削除後に順位が更新される

### 車両データ

* 各ラップに正しく紐づく
* 空欄を0として扱わない
* 修正後の値が保存される

### 戦略計算

* 3・5・10周平均が正しい
* データ不足を正しく処理する
* 周回差と時間差が混同されない
* 強制停止時間が予測に反映される
* 攻撃・防衛目標タイムが正しく算出される
* 異常値で計算が破綻しない
* 記録修正後に予測が更新される

### CSV

* 全ファイルが正しく出力される
* Excelで日本語が文字化けしない
* 日時が正しい
* メモ内の改行・カンマが壊れない
* 削除済みデータが通常記録CSVに混入しない

### 操作履歴

* 追加・編集・削除が記録される
* 操作者名が正しく保存される
* 変更前後の値が確認できる
* 取り消し操作も履歴に残る

## 19. 開発の進め方

一度に全機能を実装しない。

以下の順番で開発する。

1. プロジェクト初期化・技術構成確定
2. SQLite・Repository層
3. 大会・チーム管理
4. マスタークロック・レース時計
5. 自チームラップ記録
6. 他チーム通過記録
7. 車両データ入力
8. 操作者・メモ・操作履歴
9. CSV出力
10. 戦略計算エンジン
11. 警告判定
12. 異常終了・電源断復旧
13. 統合テスト
14. UI調整・最終検証

各段階でテストを実行し、動作を確認してから次へ進む。

未実装機能を実装済みと報告してはならない。

* 積算値の正確な意味・単位
* 大会の正式な同周回順位判定ルール
* 他チームの初回通過時刻の基準
* 強制停止時間の具体的な登録・変更条件

## Claude Codeへの最終指示

この仕様書をプロジェクトの基準文書とする。

最初に仕様を読み込み、実装計画とディレクトリ構成案を提示すること。

その後、開発段階ごとに実装・テストを行う。

仕様に矛盾や技術的な問題がある場合は、勝手に変更せず、問題点・影響範囲・修正案を提示すること。

ユーザーが決定するUI仕様を先回りして決めないこと。

最優先事項は、レース中に確実に記録できること、データを失わないこと、正しい計算結果を提示することである。
